# Fabric Vitals — Metric definitions (v0.2)

**Status:** Fabric Vitals v0.2 (draft) — a technical proposal for discussion. Not a standard. Rulebook values not yet set.

This file defines the 45 candidate metrics (M01–M45). A metric is one measured quantity, such as the number of packets a queue has dropped. Each metric feeds one of the seven vitals D1–D7, the seven health dimensions of a fabric (D1 reachability, D2 resilience, D3 congestion and loss, D4 delay and tail, D5 physical link integrity, D6 effective capacity, D7 AI communication), or it feeds the confidence output (CF), which reports how much of the fabric was actually observed. The vitals themselves are defined in [`SPEC.md`](SPEC.md) §4. Where a metric is judged against a value the fabric owner declares, the table names the spec-sheet field, written S followed by a number; the spec sheet is the owner's declaration of what the fabric promises, and its fields are listed in [`SPEC_SHEET.md`](SPEC_SHEET.md). Otherwise the metric is judged against a Rulebook parameter, written T followed by a number; the Rulebook is the register of how every fabric is measured and judged, kept in [`RULEBOOK.md`](RULEBOOK.md).

The table below gives each metric's identity and its **vendor-neutrality status**, meaning whether a published model that belongs to no single vendor defines how the metric is named and exported:
- **Vendor-neutral model exists:** the metric is carried by a model from OpenConfig (an industry project that publishes vendor-neutral data models for network devices), from the IETF (Internet Engineering Task Force, the body that publishes internet standards), from the IEEE (Institute of Electrical and Electronics Engineers, the body that publishes the Ethernet standards) or from the IBTA (InfiniBand Trade Association, the body that publishes the InfiniBand standard).
- **Partial:** a model exists for part of the metric, or the model treats the metric as optional, so a device may leave it out.
- **SAI / consortium only:** the metric is available as a SAI statistic (SAI, the Switch Abstraction Interface, is a common programming interface to switch chips) or as a feature defined by an industry consortium, with no OpenConfig or IETF model.
- **No standard:** the metric is derived by Fabric Vitals from other metrics, or it exists only as a counter specific to one device driver.

Model abbreviations used in the table:
- OC: OpenConfig, followed by the path of the data item as OpenConfig names it;
- SAI: a statistic from SAI v1.19.0. Its name is the same one that SONiC (an open-source switch operating system) uses in its COUNTERS_DB counter database [1, 2];
- IEEE: management objects from Clause 30 or Clause 45 of the IEEE 802.3 Ethernet standard, as carried in the IEEE 802.3.2 YANG model (YANG is a language for describing the data a network device can report and accept) [3, 4];
- IB: InfiniBand counters from the port's performance management agent (PMA), read through sysfs, the Linux file-system view of device counters [5];
- drv: counters from the Linux RDMA drivers, exposed as `hw_counters`, which no standard defines. RDMA (remote direct memory access) is a way for a network adapter to move data straight into another server's memory without involving that server's processor [6];
- UEC: the Ultra Ethernet Consortium's Ultra Ethernet Specification (1.0.3 is the current version [7]).

**Sampling.** No primary source establishes how often an AI fabric must be polled. A cumulative counter, one that only ever counts up (total packets dropped, for example), gives the same answer whatever the polling interval, because the reading at the end of an interval minus the reading at its start is the change over that interval. A gauge, a reading of the value right now (the present queue length, for example), is different: it misses microbursts, traffic spikes that last only microseconds, unless it is sampled at sub-millisecond intervals or replaced by a watermark, which records the highest value seen since it was last reset [8]. The resolution requirement is therefore stated as a method, Rulebook parameter T20, not as a number.

**Where the vendor-neutral gaps sit:**
- **D3 (congestion and loss):** PFC frame counts and pause duration exist only in SAI, and the IEEE 802.3.2 PFC counters are deprecated [3]. Buffer watermarks exist only in SAI. The RoCE counters on the NIC, metrics M16–M18, are specific to each driver [6].
- **D4 (delay and tail):** queue-delay watermarks exist only in SAI, and what a device writes into the in-band telemetry fields is device-specific [36].
- **D2 and D7 (resilience, AI communication):** these vitals rest on derived metrics that no standard defines, including routing convergence time, M45.
- **Configuration consistency (M43):** on the switch side, MTU, DSCP classification and ECN enablement are modelled in OpenConfig, but PFC configuration is not; only an open issue exists [52]. On the NIC side, configuration is specific to each driver.

Closing the D3 gap needs one of three things: OpenConfig models for PFC and buffers, of which only an open issue exists today [52]; a vendor-neutral set of NIC counters; or the UEC's management deliverables, which its specification says are "scheduled for a future release" [19].
