# Fabric Vitals — Metric definitions (v0.2)

**Status:** Fabric Vitals v0.2 (draft) — a technical proposal for discussion. Not a standard. Rulebook values not yet set.

This file defines the 45 candidate metrics (M01–M45). Each feeds one of the seven vitals D1–D7, the health dimensions of a fabric (D1 reachability, D2 resilience, D3 congestion and loss, D4 delay and tail, D5 physical link integrity, D6 effective capacity, D7 AI communication), defined in [`SPEC.md`](SPEC.md) §4, or the confidence output (CF). Where a metric is judged against a value the fabric owner declares, the table names the spec-sheet field (S followed by a number); the Fabric Spec Sheet is the owner's declaration of what the fabric promises, see [`SPEC_SHEET.md`](SPEC_SHEET.md). Otherwise it is judged against a Rulebook parameter (T followed by a number); the Rulebook is the register of how every fabric is measured and judged, kept in [`RULEBOOK.md`](RULEBOOK.md).

The table below gives each metric's identity and its **vendor-neutrality status**, whether a published model that belongs to no single vendor defines how the metric is named and exported:
- **Vendor-neutral model exists:** an OpenConfig, IETF, IEEE or IBTA (InfiniBand Trade Association) model carries it.
- **Partial:** a model exists for part of the metric, or the model treats the metric as optional.
- **SAI / consortium only:** available as a SAI (Switch Abstraction Interface) statistic or a consortium feature, with no OpenConfig or IETF model.
- **No standard:** derived by Fabric Vitals from other metrics, or specific to one device driver.

Model abbreviations used in the table:
- OC: OpenConfig, followed by the path of the data item;
- SAI: a SAI v1.19.0 statistic, named as in the SONiC COUNTERS_DB [1, 2];
- IEEE: 802.3 Clause 30/45 objects in the 802.3.2 YANG model [3, 4];
- IB: InfiniBand PMA (performance management agent) counters via sysfs [5];
- drv: Linux RDMA `hw_counters`, not standardized [6];
- UEC: the Ultra Ethernet Consortium's Ultra Ethernet Specification (1.0.3 current [7]).

**Sampling.** No primary source establishes how often an AI fabric's telemetry, the counters and readings its devices export, must be polled. A cumulative counter is interval-invariant when differenced; a gauge misses microbursts unless it is sampled at sub-millisecond intervals or replaced by a watermark, the highest value seen since the last reset [8]. The resolution requirement is therefore stated as a method, Rulebook parameter T20, not as a number.

**Where the vendor-neutral gaps sit:**
- **D3:** PFC counts and pause duration exist only in SAI, and the IEEE 802.3.2 PFC counters are deprecated [3]. Buffer watermarks exist only in SAI. RoCE NIC counters (M16–M18) are driver-specific [6].
- **D4:** queue-delay watermarks exist only in SAI, and in-band telemetry semantics are device-specific [36].
- **D2 and D7:** derived metrics with no standard definition, including routing convergence time (M45).
- **Configuration consistency (M43):** switch-side MTU, DSCP classification and ECN enablement are modelled in OpenConfig; PFC configuration is not (only an open issue exists [52]), and NIC-side configuration is driver-specific.

Closing the D3 gap needs one of three things: OpenConfig PFC and buffer models (only an open issue exists [52]); a vendor-neutral NIC counter set; or the UEC's management deliverables, which its specification says are "scheduled for a future release" [19].
