# Fabric Vitals — Validation programme (v0.2)

**Status:** Fabric Vitals v0.2 (draft) — a technical proposal for discussion. Not a standard. The values in the Rulebook have not yet been set.

**Purpose.** Validation is the only route to setting two kinds of value. The first kind is the category (c) values in the Rulebook, the shared set of rules and reference values that every fabric is scored against. The second kind is the promise values of the class presets, the ready-made spec sheets that describe a standard class of fabric. Values that an owner declares on a custom spec sheet are the owner's own; validation sets only the Rulebook and the presets. See [`RULEBOOK.md`](RULEBOOK.md) for the Rulebook and [`SPEC_SHEET.md`](SPEC_SHEET.md) §5 for the presets. The programme runs in three stages:
0. **Stage 0: expert critique.** The class presets and the spec-sheet template are opened to public critique through the issue tracker, before any preset value is proposed. For a preset, the critique covers its structural predicates (the true-or-false conditions on how a fabric is built) and its promise fields (the values the class promises to deliver).
1. **Stage 1: no GPUs.** GPUs (graphics processing units, the accelerator chips that do the training work) are not needed for this stage. Experiments E2, E3, E8, E9 and E12 run in a container-based emulated fabric, on telemetry (the counters and state reports that switches and network adapters produce) that is either replayed from recordings or generated by the emulation. Together they produce the first Rulebook that carries values, numbered RB-0.3.
2. **Stage 2: GPUs and hardware.** The experiments that need real switch hardware, NICs (network interface cards, the adapters that connect each server to the fabric) or GPUs follow. They set the remaining Rulebook values, the band edges (the score values at which the headline moves from one band to the next) and the preset promise values.

No experiment has been run yet. Results, offers of data and proposals for partnership are welcome as issues. See [`CONTRIBUTING.md`](CONTRIBUTING.md).

## 1. What a container-based emulated fabric can and cannot validate

A container-based emulated fabric runs switch network operating systems inside software containers rather than on switch hardware. The containers are connected by virtual links, and a real telemetry pipeline collects from them, both by streaming (the device pushes updates as they happen) and by polling (the collector asks at intervals). Such a fabric exercises the scoring machinery on realistic telemetry streams. The scoring machinery means coverage (how much of the fabric is actually measured), grace (how a gap in telemetry is carried across), gates (the critical conditions that cap the headline score when they fire), determinism (the same input always gives the same score) and value-function monotonicity (a worse input never gives a better score).

**It cannot reproduce any of the following:**
- the buffers and queueing inside the switch ASIC (application-specific integrated circuit, the chip that forwards packets);
- the behaviour at line rate (full link speed) of PFC (Priority Flow Control, a pause signal that tells a neighbour to stop sending on one traffic class so that packets are not dropped) or of ECN (Explicit Congestion Notification, a mark that a switch sets in packet headers to signal congestion before any packet is lost);
- FEC (forward error correction, the coding on a link that repairs bit errors), BER (bit error rate, the share of bits that arrive corrupted) or optics (the transceivers and fibre);
- GPU collectives (the group communication steps, such as all-reduce, that many GPUs perform together during training).

Any parameter whose value depends on those phenomena waits for the GPU and hardware stage.

| Experiment | What the emulated fabric can validate | What it cannot validate (needs a hardware lab or production data) | RB-0.3 parameters it can set |
|---|---|---|---|
| **E2** Anti-gaming (telemetry removal) | That the bounded rule, latching (a fired gate stays fired until it is cleared) and the strict T39 constraint are implemented correctly. Anti-gaming means that nobody can improve a score by switching telemetry off. Removing any subset of entities, vitals or time slices never raises the headline beyond the G-bound, the limit that the bounded rule sets. Hiding a gate-sized region yields UNSCORABLE, and the UNSCORABLE result lists the missing telemetry. This experiment runs on emulated streams and on replayed hardware telemetry alike. | Whether real ASIC and NIC counters behave as the replay assumes. Gate conditions that exist only in hardware, such as PFC storms at line rate or the FEC-driven critical condition CC6, can be exercised only through replayed or synthetic counter values. | T39 policy values (F_k, T16_k), T29 |
| **E3** False drops from telemetry gaps | The effect of collector restarts, missed polls, subscription resets and collector-to-device loss on a real telemetry pipeline. A false drop is a fall in the score caused by missing telemetry rather than by any change in the fabric. The experiment measures the false-drop rate with and without G (the grace parameter that governs how a reading is carried forward across a telemetry gap). It also measures the staleness admitted, meaning how long a real fault can stay hidden behind a carried-forward reading, for the faults the emulation can inject: a link going down, a routing change, or a black hole (traffic silently discarded). | How the telemetry agents on hardware switches behave under ASIC load. The staleness admitted for faults the emulation cannot produce: PFC storms, FEC degradation and buffer exhaustion. | T30 (the value of G per metric type; it also decides whether gauges, the metrics that report a current level, must be streamed when they serve as evidence for a critical condition), T20 resolution rules, T17 persistence for state and routing conditions |
| **E8** Determinism, scale, cross-implementation | Bit-identical replay, meaning that replaying the same telemetry gives exactly the same output every time. Reproducibility across two independent implementations of the method. Scale invariance of the vitals that derive from the topology, D1 and D2, across emulated fabric sizes: the same relative fault should score the same in a small fabric and in a large one. Consistent meaning of state and routing information across different network operating systems. | Data-plane performance and burst behaviour, which feed D6. How different vendors' ASIC counters should be read, which feeds D3 and D5. Collective effects, which feed D7. | The determinism and replay rules; the T21 event definitions |
| **E9** Monotonic urgency | That every value function (the rule that turns a measured value into a score) and the aggregation (the rule that combines the vitals into the headline) are monotone under graded inputs, meaning that a worse input never produces a better score. The graded inputs are injected counter values, plus loss and delay added by software on the virtual links. | Real BER and FEC progressions. PFC and ECN dynamics at line rate. How graded hardware faults map onto metric values. | None directly. It is a correctness check on the T25 shapes (the shapes of the value functions) once those are proposed. |
| **E12** Configuration consistency and convergence detection | Three checks, all made against the declared spec sheet. First, that metric M43 detects every injected mismatch in the lossless configuration (the settings that let traffic cross the fabric without packet loss) that the containerized network operating systems expose: MTU (maximum transmission unit, the largest packet size a link accepts), DSCP classification (Differentiated Services Code Point, the header field that marks a packet's traffic class) and whether ECN is enabled. Second, that M44 counts session flaps and churn (sessions going down and up, and routes changing). Third, that M45 measures convergence time, the time the fabric takes to settle on new paths after a link or switch failure. | Consequences at line rate, such as loss or pauses caused by a PFC mismatch; configuration on the NIC side; and convergence under real programming of the ASIC forwarding tables. | None directly. It is a correctness check on M43–M45. |

## 2. Experiments

**General setup (all lab experiments):**
- **Topology.** At least two leaf domains, meaning two separate groups of servers each under their own leaf switches, so that multi-tenant and cross-switch effects are visible. The study of the Leonardo system shows that interference between jobs appears only when the GPUs are not under the same switch [1]. See V-S1.
- **Telemetry.** Full switch and NIC telemetry at the resolution that the draft telemetry profile requires, plus an active probe mesh, which sends synthetic test packets between many points in the fabric to measure the paths directly. The probe mesh is method M-PRB; the related parameter is T28. See SPEC.md §8.1 for the telemetry profile.
- **Diversity.** Where possible, two kinds of transport: a RoCEv2 build (RDMA over Converged Ethernet, second version; RDMA is remote direct memory access, which lets one server write directly into another server's memory across the network) and an InfiniBand or UET build (Ultra Ethernet Transport, the transport defined by the Ultra Ethernet Consortium). Also two switch vendors, for the cross-vendor part of E8.
- **Scale of existing lab studies.** Alibaba's link-failure and flap experiments used a 256-GPU (32-host) testbed [2]. Juniper's validated designs were lab-tested at about 96 and 32 GPUs, with the results kept private [3, 4]. That these scales are enough is an inference, not an established fact, and it is to be tested. See E8.

| **E1** | **Directional correctness under injected faults.** For each failure scenario, start from a healthy fabric, inject one degradation, compute the score, then restore the fabric. The degradations are: a link down; optic attenuation (weakening the light signal on a fibre); BER injection; ECMP pinning (ECMP is equal-cost multipath, the way a switch spreads traffic over several equally good paths; pinning forces traffic onto one of them); oversubscription by link removal; a PFC storm from a misbehaving NIC; loss injection; a routing flap; slow convergence; a lossless-configuration mismatch; and redundancy removal. | Rulebook: T7, T9, T11, T13, T14, T16. The binding reason (the single finding that explains why the headline is what it is) names the injected cause. Gates fire only for critical conditions (the CC conditions). Recovery follows the declared hold and decay. | A vital never moves for its scenario, which means the metric set is wrong; or the binding reason regularly names the wrong cause, which means the attribution rules are wrong. |
| **E2** | **Anti-gaming: telemetry removal.** Remove entities, vitals and time slices from the telemetry, including the entities that carry an active gate, and check that the score never improves. In a small fabric every subset is removed in turn; in a large fabric random subsets are removed. See SPEC.md §8.2 for the G-bounded limit. | Any violation means the bounded rule or its implementation is wrong. This blocks the use of any profile version. |
| **E3** | **False-drop rate caused purely by telemetry gaps.** On a healthy fabric that is not changed in any way, inject collector restarts, missed polls, gNMI subscription resets (gNMI is the gRPC Network Management Interface, a streaming telemetry protocol) and network loss between the collector and the devices, at realistic frequencies and durations. Compute the score with G = 0 and again with candidate values of G. At the same time, inject a real fault during a gap to measure the staleness admitted: the delay until the fault shows in the score. | T30 (the value of G), T29, T20, T17 | A lab telemetry pipeline with a collector, streaming and polling; no GPUs are needed for the false-drop half | The false-drop rate is the fraction of windows in which the headline falls, or becomes UNSCORABLE, although nothing in the fabric changed. It should fall as G rises. The staleness admitted must stay below the persistence T17 of the conditions it could hide (the time a condition must last before it counts). | No value of G achieves both a low false-drop rate and a staleness below T17. Then the carry-forward rule is revised: for example, require streaming (on-change updates plus a heartbeat) for gauges in the telemetry profile, or exclude gate evidence from carry-forward. |
| **E4** | **Impact equivalence (commensurability, T25/T31).** Commensurability means that the same score on two different vitals stands for the same amount of harm. Construct pairs of injected conditions that place two different vitals at the same value, for example D3 = D5 = the reference-boundary anchor. Then measure the communication impact attributed to each: the deviation in synthetic busbw (bus bandwidth, the effective bandwidth that a collective benchmark reports), the JCT ratio (the ratio of job completion times between two runs) in benchmark runs [5], and the congestion impact C = T_co-run / T_isolated, the run time with other jobs sharing the fabric divided by the run time alone [6]. | T25, T31 | GPUs are required: a lab of 32–256 GPUs running synthetic collectives (method M-D7) | Equal vital values produce comparable attributed impact, within the uncertainty that E5 establishes. | A systematic mismatch means that the minimum is not commensurable, so taking the lowest vital as the headline would compare unlike things. Revise the anchors, or move toward a cap-hybrid. See SPEC.md §6. If the mismatch cannot be repaired, the aggregation design must be reconsidered before any band is published. |
| **E5** | **Robustness to value judgements.** Every composite score rests on choices that could have been made differently; this experiment tests whether those choices matter. It follows Step 7 of the handbook on composite indicators from the OECD (Organisation for Economic Co-operation and Development) and the JRC (the European Commission's Joint Research Centre) [7]. It is an uncertainty and sensitivity analysis over the aggregation rule (the minimum, a cap-hybrid, a geometric mean, or the two-stage method of ITU-T Recommendation M.3042, a telecom network-health framework; ITU-T is the telecommunication standardization sector of the International Telecommunication Union), the windows (T19), the way confidence values are combined (T23) and the choice of anchors. | T19, T23, T24, the choice of aggregator | Replay of the E1 and E4 data | The binding reason and the rank order of the headline are stable across plausible choices. | Unstable binding reasons mean the headline cannot be relied on. Revise the aggregation, or report the headline only together with its sensitivity range. |
| **E6** | **Outcome calibration and band edges.** Correlate the vital values and the headline with outcomes that have been attributed to the network: busbw against its reference [8], the JCT ratio [5], and attributed slowdown found through delay matrices or through the localization methods that operators use [9, 10]. | T22, T40 (the band edges), T15; preset values for T26 (`K_acc_D7`) and T5 | GPUs; a lab first, then shadow mode on production fabrics. See V-S2. | A monotone relationship between the score and the attributed impact. The band edges (T40) are then placed where the impact changes class. This follows the way ITU-T G.109 anchored its speech-quality bands (bands of the R rating) to tests with real users [11]. The availability measure then becomes computable without the ILLUSTRATIVE label. See SPEC.md §9.2. | No monotone relation means the index does not track impact. Revisit the metric set and the value functions before any bands are published. |
| **E7** | **Specificity, or the false-positive rate.** A false positive is a lowered score or a fired gate in a period that was in fact healthy. Measure it on labelled incidents and on replay, using public traces (the Monet data from the Blue Waters system [12], and AcmeTrace, which is job-level only [13]) and lab logs. Precedent: Meta's RSC (Research SuperCluster) tuned its health checks so that "less than 1% of successfully completed jobs observe a failed health check" [14]. | T17, T18, T21, T27, T36 | Replay | A low rate of lowered scores and fired gates in the windows labelled healthy. | A high false-positive rate means: revise the persistence, debounce and hysteresis settings (the rules that stop a brief or borderline reading from changing the score), not the reference values. |
| **E8** | **Scale invariance, cross-vendor reproducibility, determinism.** Inject the same relative fault, meaning the same share of capacity affected, at two scales, or in the lab and in a simulation. Inject the same fault on the equipment of two vendors. Replay the same telemetry through two independent implementations of the method. | Within-vital aggregation; the T35 mappings | A lab plus a simulation; the equipment of two vendors | The scores match within the uncertainty. Pure size never lowers the score. Replay is bit-identical. | Dependence on scale means: revise the intensive normalization (the rule that expresses each vital as a share of the fabric rather than as an absolute count, so that size alone does not move it). See SPEC.md §6. Dependence on vendor means: revise the semantic mappings, which translate each vendor's NIC counters into vendor-neutral meanings, or lower the confidence that comes from semantic trust. |
| **E9** | **Monotonic urgency.** Apply faults of graded severity, such as a rising BER, rising loss or longer pauses, and check that a worse fault never raises the score [15]. | The T25 shapes | Emulation or lab | The score is monotone: it never rises as the fault gets worse. | A value function that is not monotone is a defect and must be fixed. |
| **E10** | **Declared spec-sheet shortfall, the over-claim rule and the flat headline.** A shortfall is the case where the fabric as built does not meet the spec sheet declared for it. Declare a spec sheet that the lab fabric does not meet: for example, declare R2 with dual-homing (every server attached to two switches) but build R1 with single-homing (one switch per server), first fully and then partially. Check that D2 = 0 for the full over-claim and that D2 shows the delivered fraction for the partial one. Check that the counterfactual "declared R2, built as R1; as R1 it would score N" is shown. Then run the E1 faults. See SPEC.md §3. | The presentation rules; the dependence of D2, CC4 and CC5 on S4 and S10. See SPEC.md §11 for the presentation rules. | Lab | The headline is capped by the shortfall. The breadth indicator, the next-binding vital and the full-vector trend still register every E1 fault. A new spec-sheet version at the verified class restores sensitivity, in a new score series. | The E1 faults become invisible in every printed output during a shortfall. The presentation rules must then add an operational sub-vector. |
| **E11** | **No measurement disincentive.** Measuring more must never be punished. Add optional D7 runs, or extra probes, to a class that does not require them. See SPEC.md §4.3 for the D7 rule. | The role of D7 | GPUs | The headline never falls except through a finding attributed to a network element. | A fall without attribution means the D7 rule of SPEC.md §4.3 is wrongly implemented. |

## 3. Order of work and GPU needs

| Stage | Experiments | Needs GPUs? | What it sets |
|---|---|---|---|
| 1 | E2, E3, E8, E9, E12 (emulated fabric or replay) | No | The T29, T30 and T39 values; T17 for state and routing conditions; T21; the determinism rules; the M43–M45 implementation checks. Together these produce RB-0.3. |
| 0 | Expert critique, through the issue tracker | No | The structure of the class presets and of the spec-sheet template |
| 2a | E1, E10 (a lab of 32–256 GPUs) | Yes, for measurement based on collectives; also hardware switches and NICs | T7, T9, T11, T13, T14, T16; preset values for T3, T4, T12, T32; the presentation rules |
| 2b | E4, E6, E11 | Yes | T25, T31, T22, T40, T15; preset values for T26 and T5 |
| 2c | E5, run over all the data collected | No new runs | T19, T23, T24; the choice of aggregation |
| 2d | E7 on replay; V-S2–V-S6 with partners | Partly (the production shadow mode) | T17, T18, T21, T27, T36; the scale-transfer checks |

The value-function values, the band edges, the preset values and every hardware-dependent value wait for stage 2.
