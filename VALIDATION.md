# Fabric Vitals — Validation programme (v0.2)

**Status:** Fabric Vitals v0.2 (draft) — a technical proposal for discussion. Not a standard. Rulebook values not yet set.

**Purpose.** Validation is the only route to setting the category (c) values in the Rulebook, the shared rules and reference values every fabric is scored against, and the promise values of the class presets, ready-made spec sheets (owner declarations of what a fabric is built to deliver) for standard classes of fabric. Values declared by an owner on a custom spec sheet are the owner's own; validation sets the Rulebook and the presets. See [`RULEBOOK.md`](RULEBOOK.md) and [`SPEC_SHEET.md`](SPEC_SHEET.md) §5. The programme runs in three stages:
0. **Stage 0: expert critique.** Public critique of the class presets (their structural predicates, the true-or-false conditions on how a fabric is built, and their promise fields, the values the class promises to deliver) and of the spec-sheet template, through the issue tracker, before any preset value is proposed.
1. **Stage 1: no GPUs.** E2, E3, E8, E9 and E12 run on replayed or emulated telemetry (the counters and state reports that switches and NICs produce) in a container-based emulated fabric. They produce the first Rulebook with values (RB-0.3).
2. **Stage 2: GPUs and hardware.** The experiments that need real switch hardware, NICs or GPUs follow. They set the remaining Rulebook values, the band edges (where the headline, the fabric's single Vitals Score, moves from one band to the next) and the preset promise values.

No experiment has been run yet. Results, data offers and partnership proposals are welcome as issues. See [`CONTRIBUTING.md`](CONTRIBUTING.md).

## 1. What a container-based emulated fabric can and cannot validate

A container-based emulated fabric runs switch network operating systems in containers, connected by virtual links, with a real telemetry pipeline (streaming and polling collectors, the systems that gather the telemetry). It exercises the scoring machinery on realistic telemetry streams: coverage (how much of the fabric is actually measured), grace (how a telemetry gap is carried across), gates (the critical conditions that cap the headline), determinism and value-function monotonicity (a worse input never gives a better score).

**It cannot reproduce any of the following:**
- ASIC buffers and queueing;
- PFC (Priority Flow Control, a pause signal that stops a neighbour sending on one traffic class so that no packet is dropped) or ECN (Explicit Congestion Notification, a header mark that signals congestion before loss) behaviour at line rate;
- FEC (forward error correction, the link coding that repairs bit errors), BER or optics;
- GPU collectives (the group communication steps, such as all-reduce, that many GPUs perform together).

Any parameter whose value depends on those phenomena waits for the GPU and hardware stage.

## 2. Experiments

**Cross-vendor status.** Fabric Vitals is designed for vendor-neutral use, but equivalent telemetry semantics are not assumed. Some required measurements have common models today, some require vendor/platform adapters, and some counter meanings still need validation. E8 therefore tests cross-platform and cross-implementation reproducibility; a mismatch is evidence against comparability, not something to normalize away silently.

**Aggregation falsifiability.** E4 and E5 test the v0.2 weakest-vital proposal rather than confirm it. No aggregation model is designated the expected winner. The comparison includes the current `min()` rule, a calibrated weakest-vital variant whose per-vital scales/anchors are fitted against measured network-attributable workload impact, an arithmetic-average comparator to quantify compensation/masking, and the other serious alternatives already named in E5. If the evidence favors another model, the validation programme permits the aggregation design to change in a later normative version.

**General setup (all lab experiments):**
- **Topology.** At least two leaf domains, so that multi-tenant and cross-switch effects are visible. Leonardo shows that interference appears only when GPUs are not under the same switch [1]. See V-S1.
- **Telemetry.** Full switch and NIC telemetry at the resolution the draft telemetry profile requires, plus an active probe mesh (method M-PRB, T28). See SPEC.md §8.1.
- **Diversity.** Where possible, both a RoCEv2 and an InfiniBand or UET (Ultra Ethernet Transport) build, and two switch vendors (for E8 cross-vendor).
- **Scale of existing lab studies.** Alibaba's link-failure and flap experiments used a 256-GPU (32-host) testbed [2]. Juniper's validated designs were lab-tested at about 96 and 32 GPUs, with results kept private [3, 4]. That these scales suffice is an inference to be tested. See E8.
