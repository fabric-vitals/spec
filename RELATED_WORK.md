# Fabric Vitals — Related work and positioning (v0.2)

**Status:** Fabric Vitals v0.2 (draft) — a technical proposal for discussion. Not a standard. The values in the Rulebook have not yet been set.

This file is a fuller version of the paper's section on related work. It records where Fabric Vitals agrees with existing standards, drafts and practice, where it borrows from them, and where it differs from them. Facts about external documents are quoted from the primary texts wherever possible.

## 1. Summary of the landscape

The review behind this proposal covered standards bodies, industry consortia, vendor documentation, publications from universities and from hyperscale operators (the very largest cloud and AI operators), scoring methodology from other fields, and design-classification standards. The table below takes each category in turn:

| Category | Does it define a composite score? | What Fabric Vitals takes from it | Key sources |
|---|---|---|---|
| Standards bodies: ITU-T (the telecommunication standardization sector of the International Telecommunication Union), the IETF (Internet Engineering Task Force, the body that publishes Internet standards as RFCs, Requests for Comments, and their drafts as Internet-Drafts) and the IEEE (Institute of Electrical and Electronics Engineers, which publishes the Ethernet standards) | Yes, several. ITU-T M.3042 defines a network health index. ITU-T E.840 defines a relative benchmark score. ITU-T G.107 defines the R rating, a 0–100 rating of transmission quality. QoO (Quality of Outcome, an IETF draft) defines a 0–100 score taken as a minimum. SAIN (Service Assurance for Intent-based Networking, an IETF architecture) defines a 0–100 container for a score. | Containers and methods for scoring exist. There is no standardized set of AI-fabric metrics with agreed meanings. The IEEE supplies counters, and it has deprecated the PFC frame counters (PFC is Priority Flow Control, a pause signal that stops a neighbour sending on one traffic class) in its YANG data model (YANG is the language used to describe what a device can report and configure). | [1, 2, 3, 4, 5, 6] |
| Consortia and telemetry models: the UEC (Ultra Ethernet Consortium), OCP SAI (the Open Compute Project's Switch Abstraction Interface, a common programming interface to switch chips), SONiC (Software for Open Networking in the Cloud, an open-source switch operating system), OpenConfig (a vendor-neutral set of data models for network devices) and the IBTA (InfiniBand Trade Association) | None. They define only per-component states: SONiC reports OK or Not OK, and OpenConfig reports HEALTHY or UNHEALTHY. | The UEC's chain from FEC (forward error correction, the coding that repairs bit errors on a link) to UCR and then to MTBPE is the most reusable standardized method for a sub-indicator; UEC 1.0.3 is the current version. See UEC §6.3. Counters for PFC, for switch buffers and for RoCE NICs (RoCE is RDMA over Converged Ethernet; RDMA, remote direct memory access, lets one server write directly into another server's memory across the network; a NIC is the network interface card that connects a server to the fabric) have no vendor-neutral export model. | [7, 8, 9, 10, 11, 12] |
| Vendor implementations | Cisco, NVIDIA NetQ, Nokia EDA (Event-Driven Automation), Dell, Juniper DCA (Data Center Assurance) | Four patterns appear: the worst reading per device, then the percentage of devices that are healthy; the percentage of time a threshold is met; averages and weighted roll-ups; and anomalies reported without any index. None is vendor-neutral, and none is based on AI-fabric inputs. | [13, 14, 15, 16, 17] |
| Hyperscale operators, universities and HPC (high-performance computing) | ANSC, which is categorical and was tested only in simulation; the Monet bands, which their authors call "qualitative" | In this literature, "health" means pass-or-fail gates, thresholds chosen by operators, and localization (finding which component is at fault). The share of job disruption that the network causes depends on the deployment. | [18, 19, 20, 21, 22, 23] |
| Scoring methodology outside networking | The OECD/JRC handbook on composite indicators (from the Organisation for Economic Co-operation and Development and the European Commission's Joint Research Centre), the HDI (Human Development Index), Apdex (the Application Performance Index), the NBI (National Bridge Inventory) bridge condition measures, CIGRE (the international council on large electric systems, a power-industry body), Opensignal and FICO (the credit score) | Linear and geometric aggregation are compensatory: a strong result in one part can make up for a weak result in another. Safety-oriented indexes use the minimum, or permit a worst-mode reading. Uncertainty is kept beside the score, or the score is withheld. | [24, 25, 26, 27, 28, 29] |
| New IETF work (2026) | The LQS (Link Quality Score): a per-link composite of congestion, on a 0–255 scale, vendor-agnostic, for AI/ML (artificial intelligence and machine learning) fabrics built as a CLOS network (a multi-stage switching topology); how it is computed is left to each implementation | Major prior art. A candidate input to D3 and D6. Not a fabric health score. See §4. | [30, 31] |
| Design-classification standards | None; they define classes, not scores | Four ideas: a ladder vocabulary (named classes that step up in strictness); the owner declares the class before design; the lowest-rated subsystem sets the rating; and conformance is confirmed by outcome-based tests. None of them classes AI fabrics. | [32, 33, 34, 35] |

**Positioning.** Fabric Vitals is a new combination of existing pieces, not a new category. The pieces are:
- the health-index concept of ITU-T M.3042;
- the minimum aggregation (the lowest part sets the whole) used by QoO and by the inner indexes of M.3042;
- the −1 value of SAIN, which means that no score could be computed, and its rule that a score must come with the symptoms that explain it;
- the precedent of withholding a score, taken from FICO and Apdex;
- class declaration as the data-centre facility standards practise it, where the owner declares a class and the site is checked against it;
- the link-reliability method of the UEC.

What is new is combining these with AI-fabric inputs, a Rulebook shared by every fabric, a spec sheet declared for each fabric (with class presets, which are ready-made spec sheets for standard classes of fabric), reference-first normalization (every measurement is first compared with a pre-registered reference value) and bounded health (a score that cannot be raised by hiding evidence). Section 6 explains why this differs from the common view of health as a checklist of metrics.

## 2. Mapping Fabric Vitals onto ITU-T M.3042 (03/2025) [1]

ITU-T M.3042 is the principal prior work. Fabric Vitals is a separately named method, not a profile of M.3042 (a profile would be a constrained way of applying it). The mapping below lets readers who know M.3042 see exactly where the two agree and where they differ. The M.3042 facts are taken from a reading of its full text, including the appendices.

| Element | M.3042 | Fabric Vitals | Agreement or difference |
|---|---|---|---|
| Object | "A single summary indicator expressed in quantitative terms indicating the degree of communication network health". See M.3042 §3.2.2. | A single headline that confirms whether an AI fabric conforms to its declared class | The same concept; a different domain and a different definition of health |
| Scope | Operator public networks and industry private networks; the worked examples are a 5G (fifth-generation mobile) core and NFV (network functions virtualization, running network functions as software on general-purpose servers) | AI back-end scale-out fabrics (the networks that connect many GPU servers to one another), in v0.2 | A different domain |
| Level 1 (the top score) | The total T is a weighted sum of four level-2 indexes: T = w1K1 + w2K2 + w3K3 + w4K4, where each K is an index and each w is its weight; "the definition of the weights for T is outside the scope of this Recommendation". See M.3042 §7.1. | The headline is the minimum over the lower bounds of the vitals, capped by the critical conditions | Differs. Fabric Vitals is non-compensatory across vitals (a good vital cannot make up for a bad one) and needs no weights. |
| Level 2 | Four indexes, "availability, reliability, security and maintainability", each a weighted sum of the level 3 indexes. See M.3042 §6.2 and §7.2. | The vitals D1–D7 | D1 roughly corresponds to availability. D2 and D5 roughly correspond to reliability. Maintainability is covered by the spec sheet (its resilience promise and recovery objective) and by the conformance tests. Security is excluded, to keep the method focused on fabric health. |
| Level 3 | 21 indexes. 8 of them take the minimum across NE types (types of network element, that is, kinds of device): RUQR, NAR, NPQR, NEFRR, network toughness, NRPR, CERRDRPR and RRCMCR; for example, "RUQR score = min RUQRi". The other 13 are weighted sums. See M.3042 §9.2–9.3, and §9.2.1 for the example. | Within-vital aggregation: each vital is a capacity-weighted share over the designed denominator (the capacity the fabric was designed to have), and the worst entity is reported alongside | The same spirit as the inner minimum of M.3042, which is non-compensatory across element types. Fabric Vitals weights by capacity share, not by type. |
| Level 4 | Scenario-specific indexes | The metrics M01–M42. See [`METRICS.md`](METRICS.md). | Analogous |
| Normalization (turning a raw measurement into a score) | Min-max scaling, clamped to the range [qmin, qmax]. See M.3042 §7.3. | Value functions anchored to reference values. See [`SPEC.md`](SPEC.md) §5. | Differs. Fabric Vitals anchors to pre-registered references, not to limits chosen by the operator. |
| Non-compensatory devices (rules that stop a good result hiding a bad one) | Only the level-3 minimum. There is no veto, cap, override or forced level anywhere. | The minimum across vitals, plus the critical conditions, which act as caps | Fabric Vitals adds non-compensation across vitals |
| Health levels | Appendix III, which is non-integral (not a binding part of the Recommendation), assigns Healthy, Subhealthy or Unhealthy from T, with thresholds "determined by operators" | Bands are a display rule with edges T40, published only once they are calibrated; any earlier bands are labelled ILLUSTRATIVE | Both leave the edges open; Fabric Vitals states how its edges will be calibrated |
| Weights | Out of scope. The methods listed are Delphi (structured expert consensus), AHP (the analytic hierarchy process; Appendix IV says "The results should pass the AHP consistency test"), CV, PCA (principal component analysis) and entropy. See M.3042 §8.3. | None are used, because the headline is a minimum. If a compensatory element is ever adopted, the elicitation methods of M.3042 apply, under T24. | Compatible |
| Evaluation period | "The period can be week, month, quarter and year." See M.3042 §9.1. | From minutes up to daily views, set by T19 | Differs: Fabric Vitals is an operational view, M.3042 a periodic assessment |
| Testing | Network toughness is measured with chaos engineering (deliberately injecting faults to see how the network copes). See M.3042 §9.3.2 and App. V. | Outcome-based conformance tests; the validation programme | Compatible; Fabric Vitals cites M.3042 App. V as precedent |
| Status | An ITU-T Recommendation, in force, approved 2025-03-29; no amendment or revision item as of 2026-09-23 [36] | A technical proposal for discussion (v0.2) | — |

## 3. IETF AI-fabric benchmarking drafts: Fabric Health Indicators as Fabric Vitals inputs

**Status.** The drafts are draft-calabria-bmwg-ai-fabric-{terminology, training-bench, inference-bench}. They are individual Internet-Drafts (documents submitted by their authors in their own name) and have not been adopted by BMWG (the IETF's Benchmarking Methodology Working Group) [37, 38, 39]. Status on 2026-09-23: all three are -04 individual drafts, which BMWG lists as related drafts [37, 38, 39].

**Scope.** They define Fabric Health Indicators (FHIs) for benchmarking in the lab, and they state that "the definition of acceptance criteria or performance requirements is explicitly outside the scope of this Working Group" [37]. The lists of FHIs differ between the terminology draft and the two methodology drafts.

**Relationship.** Fabric Vitals is complementary to the drafts: it does not compete with them, and the FHIs map onto Fabric Vitals inputs as follows:

| FHI (and the draft that defines it) | Fabric Vitals input | Note |
|---|---|---|
| PFC event rate (terminology draft) | D3, through M12 or M13; the duration of pauses is preferred to the count of events | Parameter T3 |
| PFC storm occurrence (terminology draft) | Critical condition CC2, and M14 | |
| ECN marking ratio (terminology draft; ECN is Explicit Congestion Notification, a mark set in packet headers to signal congestion before loss) | D3, M15 | Method-only reference T1 |
| Packet loss rate (terminology draft) | D3, through M10 or M11; also critical condition CC3 | Parameter T14 |
| Buffer occupancy at P99 (terminology draft; P99 is the level that ninety-nine of every hundred samples stay below) | D3, through M19 or M20 | Parameter T9 |
| Retransmission rate (terminology draft) | D3, M18 | Parameter T4 |
| Link flap count (training-bench draft; a flap is a link going down and coming back up) | D5, M32 | Parameters T8 and T21 |
| CRC/FCS errors (both methodology drafts; the FCS, or frame check sequence, is the checksum on each Ethernet frame, computed as a CRC, a cyclic redundancy check) | D5, M31 | |
| FEC error rate and post-FEC BER (inference-bench draft; BER is the bit error rate, and post-FEC means the errors that remain after forward error correction) | D5, through M28 or M30 | The T37 budget. The draft's "< 1e-12 post-FEC BER" is an indicative range, "not pass/fail criteria", so it is not used as a reference. See §4.4 of that draft. |
| FIB or route convergence time (training-bench draft; the FIB is the forwarding information base, the table a switch forwards by) | D2, M45; the recovery objective S11, under T33 | Named explicitly in v0.2 |
| BGP/OSPF stability (inference-bench draft; BGP and OSPF, the Border Gateway Protocol and Open Shortest Path First, are routing protocols) | D1, M02, M44 | Routing stability is named explicitly in v0.2 |
| NIC QP state (inference-bench draft; a QP, or queue pair, is the endpoint of an RDMA connection on the NIC) | D3 or D1, under the NIC boundary rule. See SPEC.md §4.2. | Needs correlation across hosts |
| Switch CPU (central processing unit) and memory utilization (methodology drafts) | Not a vital. At most it reaches D1 through component health (M05), where it affects forwarding. | The health of a device is not the health of the fabric |
| Power consumption (training-bench draft) | Out of scope | |
| GPU–NIC PCIe bandwidth (inference-bench draft, marked "contextual"; the GPU is the graphics processing unit, the accelerator chip, and PCIe is the PCI Express bus that links it to the NIC inside a server) | Outside the scored path; an input to attribution. See SPEC.md §4.2. | A host-side matter |
| JCT Ratio and BusBW (training-bench draft, App. B; JCT is job completion time, and BusBW is bus bandwidth, the effective bandwidth reported by a collective benchmark) | Validation, through M40; D7, through M38 | Non-normative values (figures the draft gives for information, not as requirements) are not used as references |

**Proposed collaboration**:
- FHIs as named inputs to Fabric Vitals;
- the benchmarking methodology of the drafts as a basis for the commissioning test suite (the tests a fabric passes before it enters service), under T34;
- a shared vocabulary.

Fabric Vitals uses the word "Score" so as not to give "Indicator" a second meaning.

| LQS element | How Fabric Vitals uses it | Condition |

## 5. Other precedents

- **SAIN (RFC 9417, Informational; RFC 9418, Standards Track)** [5, 40]. SAIN is Service Assurance for Intent-based Networking. The first RFC describes the architecture and is Informational (published for information, not as a standard); the second is on the Standards Track, that is, a proposed standard. Its precedents:
  - a health score range of −1..100, where −1 means "no value could be computed";
  - "a non-maximal score must always be explained by one or more symptoms". See RFC 9417 §2.
  - the calculation is left to implementers, and the worked example in RFC 9418 is additive (it adds up parts, so a strong part can offset a weak one).

  The UNSCORABLE rule and the binding-reason rule of Fabric Vitals conform to this, and its vitals can be expressed as SAIN subservices (the components into which SAIN breaks a service down).
- **QoO (draft-ietf-ippm-qoo, WG draft in the RFC Editor queue, not an RFC)** [4]. QoO is Quality of Outcome, a working-group (WG) draft that is waiting in the RFC Editor's queue for publication. It defines a 0–100 score taken as the minimum over sub-scores, with thresholds set by an application profile. Fabric Vitals follows both the minimum and the profiles.
- **Uptime Tier Standard: Topology (2018)** [33]. The Uptime Institute's Tier standard rates a data-centre site's infrastructure. Its rules:
  - the network is excluded: the rating is "independent of the IT systems operating within the site";
  - "The site's Tier rating is not the average of the ratings … The site's Tier rating is the lowest of the individual subsystem ratings";
  - "there are no partial or fractional Tier ratings";
  - "Compliance … is measured by outcome-based confirmation tests".

  Fabric Vitals borrows the lowest-subsystem rule (the weakest part sets the rating) for the verified class, and the model of confirmation tests.
- **ANSI/BICSI 002** [35, 41]. A data-centre design standard from BICSI (the Building Industry Consulting Service International, a body for the information and communications technology infrastructure industry), approved by ANSI (the American National Standards Institute). It defines Network Infrastructure classes N0–N4 and Cable Plant classes C0–C4. The owner declares the class before design: "required performance levels of availability and reliability should be defined, prior to the start or formalization of the design". The N-class tactics (the design measures for each class) are behind a paywall and were not consulted. The Fabric Vitals class scheme is a proposal derived from the public overview, not from those tables.
- **ANSI/TIA-942-C (2024)** [32]. A data-centre standard from the TIA (Telecommunications Industry Association). It rates a site Rated-1..4. Rated-4 "has redundant capacity components, active redundant distribution paths to serve the equipment, and protection against single failure scenarios". It covers telecommunications cabling and spaces only.
- **EN 50600-2-4 / ISO/IEC TS 22237-5** [34, 42]. A European standard (EN) and its international counterpart, a technical specification (TS) from ISO/IEC (the International Organization for Standardization and the International Electrotechnical Commission). They define Availability Class 1–4 for telecommunications cabling. The requirement text is behind a paywall; the per-class wording comes from secondary sources.
- **OCP MRC 1.0 specification** (Rev 1.0, 2026-03-21; a joint contribution from AMD, Broadcom, Intel, Microsoft, NVIDIA and OpenAI) [43]. MRC is Multipath Reliable Connection, a transport that spreads one connection over several paths, published by the OCP (Open Compute Project). It defines a per-path health state machine, meaning a fixed set of states each path can be in and the rules for moving between them: GOOD, DENIED, SKIP and ASSUMED_BAD, with "Recovery is implementation-defined". It also defines a controller API (application programming interface) that "exposes telemetry and controls for integration with monitoring and orchestration agents". It defines no score and no numeric thresholds. Relevance: the MRC path states are candidate evidence for D1 and D2 on fabrics that use MRC. See §9.3.1 and §3.4 of that specification for the two quoted passages.
- **OCP ESUN Network Operator Requirements, Base Rev 1.0** (2026-02-09; authors from Meta and Microsoft) [44]. ESUN is Ethernet for Scale-Up Networking, an OCP workstream on the fabric that joins the accelerators inside one system. It treats resilience as a capability: "Resilience is required in these networks to deal with link level and path level failures." The capability is link-level retry, present or absent. It defines no health criteria. Relevance: it covers scale-up fabrics, which v0.2 deliberately excludes, since the scope of v0.2 is back-end scale-out fabrics. See §5.3 of that specification for the quoted sentence.
- **ISO 22301 / ISO/IEC 27031:2025** [45, 46]. Two business-continuity standards. In both, recovery objectives (how quickly a service must be back after a disruption) are declared by the organization and verified by exercise. This is the model for T33.

## 6. Why not a metric checklist?

A common way to describe AI-fabric health is a checklist of metrics: NIC speed, bisection bandwidth (the capacity available when the fabric is cut into two halves), oversubscription (how much more traffic the servers can offer than the uplinks can carry), tail latency (the delay seen by the slowest packets), loss, ECN and PFC activity, link utilization, job completion time (JCT) and, for inference, tokens per second. The IETF benchmarking drafts state this view for the lab. For training, "the backend network fabric determines Job Completion Time (JCT), training throughput, and accelerator utilization" [37]; for inference, the fabric determines the time to the first token, the latency between tokens, "and aggregate throughput in tokens per second (TPS)" [38]. These metrics are useful, and Fabric Vitals uses many of them as inputs. A checklist on its own, however, has five gaps. See §3 for how the metrics enter as inputs.

| Gap in the checklist view | What Fabric Vitals does instead |
|---|---|
| **It gives no verdict.** A list of numbers does not say whether the fabric is healthy. The benchmarking drafts themselves leave "acceptance criteria or performance requirements" out of scope [37]. | One verdict: the Vitals Score with its band, explained by its binding reason (the finding that holds the score down) and its contributors. See SPEC.md §6 and §11. |
| **It mixes build with operation.** NIC speed, bisection bandwidth and oversubscription describe how the fabric was built; loss, pauses and delay describe how it is running. | The build is declared on the spec sheet and checked by the conformance check; the operation is scored by the vitals against that spec sheet. See [`SPEC_SHEET.md`](SPEC_SHEET.md) §4. |
| **It judges design choices universally.** A checklist implies that more bisection bandwidth or less oversubscription is always healthier. But rail-only fabrics are meant to lack any-to-any paths [47], and one open design states that "no redundancy is assumed or required" [48]. | Each fabric is judged against its own declared promises; comparisons hold only within a class preset or between identical spec sheets. See SPEC.md §12. |
| **It counts workload performance.** JCT and tokens per second depend on the accelerators, the software, the models and the scheduling as well as on the network. One error code from a collective library (the software that runs group communication between GPUs) covers GPU crashes, network disconnection, running out of memory and faults in user code [49]. | Only evidence that can be attributed to the network is scored. Signals from jobs enter only after they have been attributed to a network element; the JCT ratio is used for validation only, through M40. See SPEC.md §4.2. |
| **It has no rule for missing data.** Unmonitored links simply drop out of the list. | Unmeasured capacity counts as unknown, never as healthy; below the coverage floor (the minimum share of capacity that must be measured), the result is UNSCORABLE, with a list of the missing telemetry. See SPEC.md §8. |
