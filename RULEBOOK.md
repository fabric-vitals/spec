# Fabric Vitals — Rulebook RB-0.2 (skeleton)

**Status:** Fabric Vitals v0.2 (draft). This is a technical proposal put forward for discussion. It is not a standard. The Rulebook values have not yet been set.

The **Rulebook** is the set of rules that says how every fabric is measured and judged. In v0.1 it was called the reference profile. The Rulebook is identical for every fabric. It holds the metric definitions and the measurement procedures; the coverage floor, which is the least telemetry a fabric must export before it can be scored at all; the blast-radius threshold, which is how much capacity a problem must affect before it counts as critical; the grace period, which is how late data may arrive before it counts as missing; the definitions of the critical conditions and the cap they place on the score; the UNSCORABLE rules; the time windows; the band edges; and the versioning rules. What each fabric promises is declared separately, on its **Fabric Spec Sheet**. Think of a car: every model's range is measured by the same official test procedure and compared with that model's own rated range. In the same way, every Vitals Score applies the same Rulebook to the fabric's own spec sheet. See [`SPEC_SHEET.md`](SPEC_SHEET.md).

This file is a **skeleton**. It gives the frame, and with one exception it gives no values:
- It fixes the structure of the Rulebook. For every parameter it says whether the parameter belongs to the Rulebook, and so is the same for all fabrics, or to the spec sheet, and so is declared by each fabric's owner.
- For every Rulebook parameter it fixes the reference category, meaning what kind of authority the value will rest on, and the basis for it.
- For parameters in category (d), where no single number can apply to all fabrics, it fixes the method that produces each fabric's own value.
- For parameters in category (c), where Fabric Vitals itself must define the value, it names the evidence needed to set that value.
- For spec-sheet parameters it names the evidence needed to set the class preset values. A class preset is a published, ready-made spec sheet that an owner may adopt instead of writing a custom one.

**It sets no values.** The one exception is T37, where a budget already exists in an IEEE standard. IEEE is the Institute of Electrical and Electronics Engineers, the body that publishes the Ethernet standards.

No score can be computed against RB-0.2 as published. The Rulebook values must first be set and frozen in a later Rulebook version, RB-0.3 or later. Setting them follows the validation programme, which is the planned series of experiments and studies that supply the evidence, and the change process. See [`VALIDATION.md`](VALIDATION.md), §6 and [`GOVERNANCE.md`](GOVERNANCE.md).

## 1. Conventions

**Rulebook / Spec sheet.** This is the new column in the parameter register. It says who owns each parameter:
- **Rulebook:** how we judge. There is one value or one method for all fabrics. It may be keyed, meaning there is a separate value for each declared attribute such as the transport or the PHY type. PHY is the physical layer of a link: the optics, cables and electrical signalling. The status is VALUE NOT SET until validation sets the value.
- **Spec sheet:** a promise made by one fabric. The owner declares the value on the spec sheet, in one of the fields S1–S23. The status is VALUE DECLARED BY OWNER. The class presets carry PROPOSED values, which are not yet set.
- **Both:** the Rulebook fixes how the thing is measured, and the owner declares the promised value on the spec sheet.

**Reference category.** This says what a Rulebook value, or a preset value for a spec-sheet parameter, rests on:
- **(a) STANDARD EXISTS.** The value comes from a formal document of an SDO, a standards development organization, meaning a recognised body that publishes standards. Examples are an IEEE standard; an IETF Standards-Track RFC, where the IETF is the Internet Engineering Task Force, an RFC is one of its published documents, and Standards-Track means the document is on the path to becoming an Internet Standard; an ITU-T Recommendation, from the telecommunication standardization arm of the International Telecommunication Union; or a standard from ISO/IEC (the International Organization for Standardization and the International Electrotechnical Commission), EN (a European standard) or ANSI (the American National Standards Institute).
- **(b) BEST PRACTICE EXISTS.** The value comes from something below an SDO standard. Such sources are graded from strongest to weakest: a consortium specification (CONSORTIUM SPEC); then a best practice shared by several vendors or by a community (multi-vendor/community BP, where BP is best practice); then the practice of a single operator; then a single vendor's reference design; then marketing material. The owner of the practice is always named. Values from the two lowest grades may be used only as declared, graded references for their own technology. That restriction is a design rule of Fabric Vitals.
- **(c) MUST BE DEFINED BY FABRIC VITALS.** Fabric Vitals itself has to define the value. The entry names the experiment or the evidence that would justify a value.
- **(d) METHOD ONLY.** No single number can apply to every fabric. The entry standardizes the procedure instead, and each fabric's own value is produced by running that procedure.

**Status:**
- **VALUE NOT SET:** a Rulebook entry that has no value yet.
- **VALUE DECLARED BY OWNER:** a spec-sheet entry, and the declared half of a "Both" entry.
- **BUDGET CITED:** T37 only. There an existing standard's budget is cited instead of a value being set.
- **CONSTRAINT DEFINED:** T39 only. It states a rule that ties other parameters together and sets no value of its own.

**Freeze point.** This is the moment a value is pre-registered, meaning written down and fixed before any scoring that uses it:
- **PV:** the value is frozen when the Rulebook version that sets it is published. It then applies to every fabric using that version. Preset values are also frozen at PV.
- **DC:** the value is frozen when the fabric's spec sheet is declared. This happens once per fabric. See [`SPEC.md`](SPEC.md) §2.
- **CM:** the value is frozen at commissioning registration, the point after burn-in when the fabric's own measured references are recorded. This happens once per fabric. The value is re-registered only by a versioned event, meaning a recorded change that carries a new version. See §4.3.

No value may change after its freeze point. The only routes are a new Rulebook version for PV entries, a new spec-sheet version for DC entries, or a versioned re-registration for CM entries. This is the no-post-hoc-tuning rule: values may not be adjusted after the fact to change a result. See §6.

**Class dependence.** This says whether one value serves every class of fabric:
- **None:** one value serves all classes.
- **Keyed:** there is a separate value for each class preset, or for each value of a declared attribute.
- **Predicate:** the entry applies only where a stated condition, the predicate named in the entry, is true.

**Named constants.** Several category (d) methods contain named constants, written `K_…`. These are the numbers a method leaves open, such as a window length or a repetition count. A method is fully specified once its named constants are set at the stated freeze point. Two operators using the same Rulebook version then run exactly the same procedure.

## 2. Parameter register

Numbers in square brackets point to the References section at the end of this file.

How to read the register. Each row is one parameter. The column "Where used" names what the parameter feeds: a vital, written D1 to D7 (the seven measured qualities of a fabric from which the score is built); a metric, written with an M-number and defined in [`METRICS.md`](METRICS.md); a critical condition, written with a CC-number (the conditions that cap the score); or a section of the specification. Spec-sheet fields are written with an S-number. Experiments are written with an E-number and studies with a V-S-number; both belong to the validation programme. Constants written `K_…` are the named constants of §1. The abbreviation "CC mode" is different from the CC-numbers: it means the congestion-control mode, the mechanism that slows senders down when the network is busy. "p50" is the median of a set of samples, and "p99" is the tail value, the level that all but the worst one per cent of samples stay under. "Job-bearing capacity" is the part of the fabric's capacity that carries jobs. Category (c) rows say what evidence would set the value; category (d) rows give the method.

## 3. Class presets

In v0.1 fabrics were graded by a scheme of design-class predicates. That scheme has become the set of **class presets**: published spec sheets that carry both structural predicates, which are conditions the build must meet, and promise fields, which are values the owner commits to. The presets are in SPEC_SHEET.md §5. They are PROPOSED and open for critique. Their values are parameter T32 together with the preset columns of T3, T4, T5, T10, T12, T26 and T33.

## 4. Declaration and conformance procedures

**4.1 Declaration (per fabric; freeze point DC).**
1. The owner fills in the spec sheet, using the template in SPEC_SHEET.md §2. It covers: the fabric scope and inventory, with the job-bearing capacity, in field S1; the scoring scopes, S23; the purpose and workload profile, S2; the build, S3–S9; the resilience promise, S10 and S11; the availability target, S12; the performance envelope, S13–S18; the required tests and the telemetry profile, S19 and S20; and the declared class, S21.
2. The class, whether a preset or a custom one, is chosen from a business-impact input: what downtime would cost, and how much disruption is allowable for each failure class. This follows the public BICSI overview and the ISO 22301 preview [44, 48].
3. The spec sheet is signed, dated and versioned, field S22. A new spec-sheet version, for example one that moves to the class actually built after an honest shortfall, starts a new score series. See SPEC.md §12.

**4.2 Conformance check (result: CONFORMANT / NON-CONFORMANT (failed predicates listed) / NOT ASSESSED).**
1. **Static:** evaluate every structural predicate against the declared build, the topology discovered by LLDP (the Link Layer Discovery Protocol, by which neighbouring devices announce themselves to each other), the inventory and the running configuration. This includes the lossless-transport configuration consistency check, predicate P-CFG, field S8.
2. **Computed:** a residual-capacity analysis under the failures the fabric declares it tolerates, field S10, using predicates P-K and P-FD.
3. **Outcome-based:** controlled failure or drain tests (a drain takes a device out of service on purpose) for each failure class in S10, measured with method M-D7. The measured recovery times and routing convergence times are compared with the objectives declared in S11. This follows the outcome-based confirmation tests of the Uptime Institute [61] and the exercises of ISO/IEC 27031 [49]. It is run at commissioning and then at the cadence `K_conf` declared in S19.
4. Record the verified class, which is the most redundant preset whose structural predicates all hold, together with the date, the type of evidence, and who attested it, whether the owner or a third party.

The score is computed against the declared spec sheet. The verified class and the conformance status are printed beside it. See SPEC.md §3 and §11.

**4.3 Commissioning registration (freeze point CM).**
1. The fabric first leaves burn-in, as defined in T36.
2. The T34 test suite is run.
3. The fabric's own method references are registered together with the M-SUITE record: the ECN and CNP references, T1 and T2, and the measured tail delay and collective bandwidth, T10 and T26. Each is checked against the value declared on the spec sheet and, for a preset, against the preset acceptance criterion.
4. Re-registration is a versioned event. It is triggered by a configuration change that touches a declared parameter, such as the ECN thresholds or the congestion-control mode; by a hardware change larger than `K_chg`; or by a new spec-sheet version.

A fabric that misses a declared value or an acceptance criterion at commissioning is still registered, and its conformance status records the failure. The failed measurement is never quietly adopted as the reference.

## 5. Minimum telemetry profile: structure

For each class preset there is a table with one row per combination of entity class, vital and metric. Each row holds:
- the metric ID, as defined in METRICS.md;
- the vendor-neutral data-model path, or the per-driver mapping;
- the metric type: counter, gauge, watermark, event or histogram;
- the declared sampling interval Δ and the resolution requirement from T20;
- the grace period G from T30;
- whether the metric is required for coverage under T29, or optional;
- which critical conditions' evidence sets the metric belongs to, as T39 requires.

The telemetry profile the owner declares in S20 must cover this minimum. A metric that a predicate declares NOT APPLICABLE, for example CNPs on a fabric without DCQCN, is removed from the coverage denominator, the total against which coverage is counted. Only a predicate can remove a metric in this way; a metric that is simply not exported cannot be removed.

## 6. Governance

- **Steward:** datacenternetwork.ai is the initial publisher and steward of the Rulebook and the class presets. The method is vendor-neutral, and stewardship may later move to a neutral body. The details are in GOVERNANCE.md.
- **Versioning:** versions are numbered `RB-<major>.<minor>`.
  - A new major version changes the structure, the categories or the methods. During the 0.x series, any version may also change the structure.
  - A new minor version sets or revises values, including preset values.
  - Every score records the Rulebook version and the spec-sheet version it was computed against. Scores computed under different versions are never compared without being recomputed. See SPEC.md §12.
- **Change process:**
  1. An open, public change log. Each change request carries its rationale and its evidence, including the ID of the experiment in the validation programme that supports it.
  2. A public comment period.
  3. A decision record.
  4. A new version number.

  A change to a category (a) or (b) reference cites the new source and its grade. A change to a category (c) value cites the experiment that justifies it.
- **No-post-hoc-tuning rule:**
  - Values are frozen at their freeze point, as set out in §1.
  - A value may not be changed in order to alter the score of a measurement window that has already begun.
  - A re-registration, freeze point CM, or a new spec-sheet version, freeze point DC, applies only to windows after its effective time, and it is visible in the score record. See SPEC.md §12.
- **Conflict of interest:** the steward's own products receive no special treatment in the Rulebook or in the presets. A proposed change from any party, including the steward, follows the same process.
