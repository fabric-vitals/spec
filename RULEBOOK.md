# Fabric Vitals — Rulebook RB-0.2 (skeleton)

**Status:** Fabric Vitals v0.2 (draft) — a technical proposal for discussion. Not a standard. Rulebook values not yet set.

The **Rulebook** (called the reference profile in v0.1) says how every fabric is measured and judged. It is **identical for every fabric**: metric definitions and measurement procedures, the coverage floor, the blast-radius threshold, the grace period, the critical-condition definitions and cap, the UNSCORABLE rules, the temporal windows, the band edges and the versioning rules. What each fabric *promises* is declared separately, on its **Fabric Spec Sheet** ([`SPEC_SHEET.md`](SPEC_SHEET.md)). Like every car's range measured by the same official test procedure against its own rated range, every Vitals Score applies the same Rulebook to the fabric's own spec sheet.

This file is a **skeleton**:
- It fixes the Rulebook's structure, and for every parameter says whether it belongs to the Rulebook or to the spec sheet.
- For every Rulebook parameter it fixes the reference category and its basis.
- For category (d) parameters it fixes the method.
- For category (c) parameters it names the evidence needed to set a value.
- For spec-sheet parameters it names the evidence needed to set the **class preset** values.

**It sets no values**, except T37, where an IEEE budget exists.

A score cannot be computed against RB-0.2 as published. The Rulebook values must first be set and frozen in a later Rulebook version (RB-0.3 or later), following the validation programme ([`VALIDATION.md`](VALIDATION.md)) and the change process (§6 below; [`GOVERNANCE.md`](GOVERNANCE.md)).

## 1. Conventions

**Rulebook / Spec sheet** (the new column in the register):
- **Rulebook:** how we judge. One value or method for all fabrics, possibly keyed by a declared attribute such as transport or PHY type. Status VALUE NOT SET until validation sets it.
- **Spec sheet:** a per-fabric promise. The owner declares the value on the spec sheet (field S1–S23). Status VALUE DECLARED BY OWNER. Class presets carry PROPOSED values, not yet set.
- **Both:** the Rulebook fixes the measurement method, and the owner declares the promised value on the spec sheet.

**Reference category** (the basis of a Rulebook value, or of a preset value for spec-sheet parameters):
- **(a) STANDARD EXISTS.** A formal SDO document: IEEE, an IETF Standards-Track RFC, an ITU-T Recommendation, ISO/IEC, EN or ANSI.
- **(b) BEST PRACTICE EXISTS.** Anything below an SDO standard, graded CONSORTIUM SPEC > multi-vendor/community BP > single-operator practice > single-vendor reference design > marketing. The owner of the practice is always named. Values at the two lowest grades may be used **only as declared, graded references for their own technology** (a design rule of Fabric Vitals).
- **(c) MUST BE DEFINED BY FABRIC VITALS.** The entry names the experiment or evidence that would justify a value.
- **(d) METHOD ONLY.** No universal number can exist. The entry standardizes the procedure, and the fabric-specific value is produced by that procedure.

**Status:**
- **VALUE NOT SET:** Rulebook entries without a value.
- **VALUE DECLARED BY OWNER:** spec-sheet entries (and the declared half of "Both" entries).
- **BUDGET CITED:** T37 only.
- **CONSTRAINT DEFINED:** T39, which relates other parameters and sets no value itself.

**Freeze point**, meaning when the value is pre-registered:
- **PV:** at publication of the Rulebook version that sets it. It is global for all fabrics using that version. Preset values are also frozen at PV.
- **DC:** at declaration of the fabric's spec sheet ([`SPEC.md`](SPEC.md) §2), per fabric.
- **CM:** at commissioning registration (§4.3), per fabric. It is re-registered only by a versioned event.

No value may change after its freeze point except by a new Rulebook version (PV entries), a new spec-sheet version (DC entries) or a versioned re-registration (CM entries). This is the no-post-hoc-tuning rule (§6).

**Class dependence:**
- **None:** one value for all classes.
- **Keyed:** a separate value per class preset or declared attribute.
- **Predicate:** the entry applies only where the predicate named in the entry holds.

**Named constants.** Several (d) methods contain named constants (written `K_…`). A method is fully specified once its named constants are set at the stated freeze point. Two operators using the same Rulebook version then run the identical procedure.

## 3. Class presets

The design-class predicate scheme of v0.1 is now the set of **class presets**: published spec sheets carrying both structural predicates and promise fields. It is in [`SPEC_SHEET.md`](SPEC_SHEET.md) §5, **PROPOSED and open for critique**. Its values are parameter T32 and the preset columns of T3, T4, T5, T10, T12, T26 and T33.

## 4. Declaration and conformance procedures

**4.1 Declaration (per fabric; freeze point DC).**
1. The owner fills in the spec sheet ([`SPEC_SHEET.md`](SPEC_SHEET.md) §2): the fabric scope and inventory with the job-bearing capacity (S1); the scoring scopes (S23); the purpose and workload profile (S2); the build (S3–S9); the resilience promise (S10, S11); the availability target (S12); the performance envelope (S13–S18); the required tests and telemetry profile (S19, S20); the declared class (S21).
2. The class, whether a preset or custom, is chosen from a business-impact input: the impact of downtime and the allowable disruption per failure class (after the public BICSI overview and the ISO 22301 preview [44, 48]).
3. The spec sheet is signed, dated and versioned (S22). A **new spec-sheet version** (for example to the class actually built, after an honest shortfall) starts a new score series ([`SPEC.md`](SPEC.md) §12).

**4.2 Conformance check (result: CONFORMANT / NON-CONFORMANT (failed predicates listed) / NOT ASSESSED).**
1. **Static:** evaluate every structural predicate against the declared build, the discovered topology (LLDP), the inventory and the running configuration, including the lossless-transport configuration consistency (P-CFG, S8).
2. **Computed:** residual-capacity analysis under the declared tolerated failures (S10: P-K, P-FD).
3. **Outcome-based:** controlled failure or drain tests for each failure class in S10, measured with M-D7, and the measured recovery and routing convergence times compared with S11. This follows Uptime's outcome-based confirmation tests [61] and ISO/IEC 27031 exercises [49]. It is run at commissioning and at cadence `K_conf` (S19).
4. Record the verified class (the most redundant preset whose structural predicates all hold), the date, the evidence type, and the attester (self or third party).

The score is **computed against the declared spec sheet** ([`SPEC.md`](SPEC.md) §3). The verified class and conformance status are printed beside it ([`SPEC.md`](SPEC.md) §11).

**4.3 Commissioning registration (freeze point CM).**
1. The fabric first leaves burn-in (T36).
2. The T34 suite is run.
3. The per-fabric method references are registered with the M-SUITE record: the ECN and CNP references (T1, T2), and the measured tail delay and collective bandwidth (T10, T26), each checked against the value declared on the spec sheet and, for a preset, against the preset acceptance criterion.
4. Re-registration is a versioned event. It is triggered by a configuration change that touches a declared parameter (e.g. ECN thresholds, congestion-control mode), a hardware change beyond `K_chg`, or a new spec-sheet version.

A fabric that fails a declared value or an acceptance criterion at commissioning is registered, and its conformance status records the failure. The failed measurement is never silently adopted as the reference.

## 5. Minimum telemetry profile: structure

Per class preset, a table with one row per (entity class, vital, metric) containing:
- metric ID ([`METRICS.md`](METRICS.md));
- the vendor-neutral model path or per-driver mapping;
- metric type (counter / gauge / watermark / event / histogram);
- declared sampling interval Δ and resolution requirement (T20);
- grace G (T30);
- whether it is required for coverage (T29) or optional;
- which critical conditions' evidence sets it belongs to (T39).

The owner's declared telemetry profile (S20) must cover this minimum. A metric declared NOT APPLICABLE by a predicate (e.g. CNP without DCQCN) is removed from the coverage denominator. Only a predicate can do that; a missing export cannot.

## 6. Governance

- **Steward:** datacenternetwork.ai is the initial publisher and steward of the Rulebook and the class presets. The method is vendor-neutral, and stewardship may move to a neutral body ([`GOVERNANCE.md`](GOVERNANCE.md)).
- **Versioning:** `RB-<major>.<minor>`.
  - A major version changes structure, categories or methods. During the 0.x series any version may also change structure.
  - A minor version sets or revises values, including preset values.
  - Every score records the Rulebook version and the spec-sheet version it was computed against. Scores under different versions are never compared without recomputation ([`SPEC.md`](SPEC.md) §12).
- **Change process:**
  1. An open, public change log. Each change request carries its rationale and evidence, including the experiment ID from [`VALIDATION.md`](VALIDATION.md).
  2. A public comment period.
  3. A decision record.
  4. A new version number.

  Changes to (a)/(b) references cite the new source and its grade. Changes to (c) values cite the experiment that justifies them.
- **No-post-hoc-tuning rule:**
  - Values are frozen at their freeze point (§1).
  - A value may not be changed to alter the score of a measurement window that has already begun.
  - A re-registration (CM) or a new spec-sheet version (DC) applies only to windows after its effective time, and is visible in the score record ([`SPEC.md`](SPEC.md) §12).
- **Conflict of interest:** the steward's own products receive no special treatment in the Rulebook or the presets. Proposed changes from any party follow the same process.
