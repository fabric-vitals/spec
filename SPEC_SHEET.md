# Fabric Vitals — Fabric Spec Sheet and class presets (v0.2)

**Status:** Fabric Vitals v0.2 (draft) — a technical proposal for discussion. Not a standard. Rulebook values not yet set.

Fabric Vitals is a method for scoring the health of an AI data-center fabric: the network of switches, links and server network adapters that carries traffic between the accelerators of a cluster (the GPUs, graphics processing units, or similar chips that run AI jobs). The method produces one headline number, the Vitals Score, which says how well the fabric is keeping the promises made for it. This document is about those promises. It is written for the fabric's owner, the party accountable for the fabric, who is often also the operator that runs it, and for anyone who reads or checks an owner's declaration.

Fabric Vitals separates two things that the earlier draft, v0.1, kept together in a single register, one list of parameters:
- **The Rulebook** says how every fabric is measured and judged. It is identical for every fabric. It is the file [`RULEBOOK.md`](RULEBOOK.md).
- **The Fabric Spec Sheet** (this file) says what this fabric promises. The owner fills it in before measurement starts, and the Vitals Score then confirms whether the fabric keeps those promises.

The model is the car. Every car's range is measured by the same official test procedure, but each car has its own rated range. The test procedure is the Rulebook, and the rated range is on the car's spec sheet. The standard models in a maker's range are the **class presets**: ready-made, complete spec sheets for common fabric designs, which an owner can adopt instead of writing a custom one. Presets are different designs for different jobs, not better and worse versions of one design. See §5.

What to do with this file: read the rules in §1, then fill in every field of the template in §2 before any measurement starts. A fillable copy of the template is the file [`templates/fabric-spec-sheet.yaml`](templates/fabric-spec-sheet.yaml). The main specification, the file [`SPEC.md`](SPEC.md), holds the binding requirements for declaring a spec sheet and for checking a fabric against it. This file holds the template itself, the mapping that says which measurement checks which field, and the presets. See SPEC.md §2 and §3.

## 1. Rules for a spec sheet

1. **Declared before measurement.** No measurement window counts toward a Vitals Score until a spec sheet is in force. See SPEC.md §2.
2. **Signed, dated and versioned.** A change to any field creates a new spec-sheet version. Scores produced under different versions form separate series: they are kept as separate histories and are not joined into one. See SPEC.md §12.
3. **Preset or custom.** The owner either adopts a class preset unchanged, or declares a custom spec sheet. A custom sheet must not carry a preset's class name. See §5.
4. **No laxer than a standard.** Where a field has a published standard behind it (today that is only the physical-layer budgets, field S18), the owner may declare a value stricter than the standard, but never a laxer one.
5. **Checked two ways.** The build fields describe how the fabric is constructed. They are checked by the conformance check, which compares the fabric as built with what the sheet declares. The promise fields describe what the fabric will deliver. They are checked continuously by the vitals (the seven measured dimensions of fabric health, D1 to D7), by the critical conditions (named fault states, CC1 to CC6, that cap the score while they are active) and by the availability measure (the share of time the fabric is healthy). See SPEC.md §3, and §4 below.
6. **Scoring scope.** A scoring scope is the unit of the fabric that is scored as one, declared in field S23. Every vital, every coverage figure (coverage is the share of declared capacity that telemetry actually reports on) and every critical-condition threshold is computed within one scoring scope, never blended across scopes. See SPEC.md §2.6.
7. **Comparability.** Scores are comparable only between fabrics on the same class preset, or on identical spec sheets, under the same Rulebook version. See SPEC.md §12.

## 2. The template

Field IDs S1–S23 are used throughout the specification. In the table, "What the owner declares" says in plain words what goes in the field. "Register" names the Rulebook entry that the field supplies a value for: either a Rulebook parameter, whose IDs begin with T, or a design predicate, a yes-or-no test of the build, whose IDs begin with P. "Checked by" names what confirms the promise: a vital (IDs D1 to D7), a critical condition (IDs CC1 to CC6), a metric from the metric catalogue, the file [`METRICS.md`](METRICS.md) (IDs beginning with M), or the conformance check. Names in code style such as `K_planes` stand for numeric quantities whose values are not yet set.

|---|---|---|---|---|---|
| S1 | Identity | **Fabric scope and inventory** | The switches, links and NIC ports (NIC: network interface card, the network adapter in each server) that the sheet covers, and which of that capacity is job-bearing, that is, carries accelerator jobs. v0.2 covers back-end scale-out fabrics: the network that carries accelerator traffic between servers. | — | Supplies the inventory that every vital, and the coverage figure, is computed against |
| S2 | Identity | **Purpose and workload profile** | Purpose: training, inference or mixed. Scoring profile: TRAINING, INFERENCE or GENERAL, the set of scoring choices that fits that kind of work. | S3 | Build | **Topology** | The number of switch tiers and the shape of the fabric: Clos (a leaf-and-spine layout with several stages), rail-optimized (the NIC in a given position on every server connects to the same leaf, forming a rail), rail-only (rails alone, with no paths between every pair of accelerators) or multi-plane (several independent, parallel copies of the fabric); and the designed paths between each pair of endpoints | P-PATH | The conformance check, by static review of the declared build; the reachability vital D1 |

## 3. The lossless-transport configuration check (S8)

**Why it is named.** Configuration errors are a documented cause of failure in lossless RDMA fabrics (fabrics that carry RDMA traffic without dropping packets). In Meta's RoCE fabrics (RoCE is RDMA over Converged Ethernet), congestion drops were "uncommon and observed mostly due to misconfiguration" [1]. Microsoft reports a production incident "caused by the buffer misconfiguration of a newly introduced switch type", whose pause frames spread and affected thousands of servers, and runs "a configuration monitoring service to check if the running configurations of the switches and the servers are the same as their desired configurations" [2]. Lossless operation depends on switches and NICs agreeing: "DSCP-based PFC requires both NICs and switches to classify and queue packets based on the DSCP value" [2].

**What is checked.** For every declared lossless traffic class, on every job-bearing path (from the sending NIC, through the switches, to the receiving NIC):
1. the same priorities are PFC-enabled on every hop and on both NICs;
2. ECN marking is enabled, with the declared configuration, on every queue that carries the class;
3. the DSCP-to-traffic-class mapping is identical on every switch and NIC;
4. the MTU is consistent along the path.

**How it enters the score.**
- **At declaration and conformance.** Field S8 is the predicate P-CFG. A path whose running configuration differs from S8 fails the predicate, and the conformance status lists it. See SPEC.md §3.
- **In operation.** Where the running configuration can be read, a live mismatch is evidence for the congestion-and-loss vital D3, as metric M43. It lowers D3 for the affected capacity and produces a mandatory finding tagged OPERATIONAL. It is not a critical condition in v0.2, because the consequences that matter are already capped by the existing conditions: sustained loss by CC3, pause storms (PFC pauses spreading from hop to hop) by CC2, and black holes (paths that silently drop traffic) by CC1.
- **Vendor-neutral visibility is partial.** OpenConfig, the vendor-neutral set of data models for reading switch state and configuration, covers switch-side MTU, DSCP classification and ECN enablement. It has no model for PFC configuration, and NIC-side configuration is driver-specific. See METRICS.md M43.

## 5. Class presets

**Status: PROPOSED — open for critique.** The class scheme is the author's proposal. It is derived from public sources on facility tiers and availability classes [3, 4, 5, 6, 7, 8, 9] and from published AI-fabric designs [1, 10, 11]. It is not derived from the requirement tables of any paywalled standard, which were not consulted.

**What a preset is.** A class preset is a published, complete spec sheet. It has two kinds of content: its **structural predicates**, the yes-or-no tests that describe the build a fabric must have, and its **promise fields**, what a fabric of that class promises to deliver.

**Classes are design patterns, not quality tiers.** The three presets are ordered by the amount of redundancy they build in, not by how good they are. A fabric that keeps the promises of its class is healthy, whichever class it is. Scores are never ranked across classes. See SPEC.md §12.

| Code | Name | Description | Evidence for the pattern |
|---|---|---|---|
| **R1** | Rail-optimized, single-homed | The most common training design in published reference designs today. Each accelerator NIC attaches to one leaf switch of its rail, and recovery from a leaf failure is by checkpoint restart: the job restarts from its last saved state. | Juniper's validated design: "rail Nth connects all GPUs in position Nth on all the servers, to leaf node Nth" [12]; NVIDIA's reference compute fabric "is rail-optimized" [13]; Alibaba calls single-ToR attachment (a ToR is a top-of-rack switch, the leaf switch in the cabinet) "widely used in the majority of current cloud providers" [10]. |
| **R2** | Dual-homed | Rides through a leaf failure, or a bounded number of uplink failures per rail, without losing capacity. | Alibaba's HPN network "connects two ports of each NIC to different ToRs in an active-active way. … If one ToR (or a port) is down, the other can still work", in production [10]. |
| **R3** | Multi-plane, sprayed, tested | Independent planes, packet spraying across them, and continuous synthetic collective tests (the AI-communication vital D7 is required). | Multi-plane spraying rides out tier-to-tier link failures [11]; a vendor reference design prescribes dual planes [14]. |

The preset's name fixes its structural pattern: single-homed, dual-homed, or multi-plane with spraying. The numeric values of its predicates, and all of its promise values, are still open, as the table below shows.

**Why failure consequence, not path counts.** Facility standards count distribution paths [4, 6]. Several AI designs, however, attach each NIC to a single rail switch by design [12, 13], and one open design states that "no redundancy is assumed or required" [15]. In AI fabrics, resilience comes instead from planes and spraying [11], from dual attachment [10] or from designed spare capacity; Meta chose an under-subscription ratio "to allow for buffer for up to two link failures" [1]. Presets are therefore stated in terms of failure consequence, meaning what the fabric absorbs and how it recovers (fields S10 and S11), rather than in path counts.

**Preset fields.** Every preset fills in the same fields. All values are PROPOSED and not set, except the physical-layer budgets in S18, where the IEEE budget applies.

**Where each structural predicate comes from.** The table gives, for each predicate family, the form in which it can be checked, the evidence used to check it, and the source it is borrowed from. The grade in brackets says how strong that source is, using the Rulebook's grading of references: a standard, an operator group, a single operator's practice, or a single vendor's reference design. See RULEBOOK.md §1.

| Predicate family | Checkable form | Evidence for the check | Borrowed from (grade) |
|---|---|---|---|
| P-HOME: host attachment | each accelerator NIC is single-homed, dual-homed to distinct leaves, or attached to at least `K_planes` independent planes | The declared intent compared with LLDP (Link Layer Discovery Protocol, by which each switch learns what is at the other end of each cable) and with the cabling records, through metric M06 | Alibaba dual-ToR (single-operator) [10]; multi-plane (operator group) [11]; NVIDIA dual-plane reference design (single-vendor) [14] |
| P-PATH: path diversity per tier | at least `K_paths(tier)` disjoint equal-cost paths between any two leaves in scope | The topology model, through metric M07 | The facility ladder concept, the graded levels of the facility standards (standard, cabling only) [4, 6] |
| P-SUB: subscription | leaf uplink capacity divided by downlink capacity is at least the declared ratio | The inventory | Vendor designs (single-vendor) [12] |
| P-TX: transport and load distribution | the declared transport (RoCEv2, UET or InfiniBand), congestion-control mode (for example DCQCN on or off), and flow hashing or packet spraying | A snapshot of the configuration | — |
| P-CFG: lossless-transport configuration | PFC priorities, ECN configuration, DSCP-to-class mapping and MTU consistent across switches and NICs on every job-bearing path | The running configuration compared with S8, through metric M43. See §3. | Operator practice (single-operator) [1, 2] |
| P-PHY: physical diversity | cabling between cabinets meets the declared cabling availability class | Declaration and audit | The data-centre cabling standards EN 50600-2-4 / ISO/IEC TS 22237-5 and TIA-942-C (standard) [4, 6] |

| P-FD: failure domain | no single component whose failure removes more than `K_fd` of job-bearing capacity | Computed | The Uptime Institute's "Fault Tolerant" tier concept (proprietary standard) [3] |

**Verified class.** A fabric's verified class is the most redundant preset whose structural predicates all hold on the fabric as built. This follows the facility rule that a site's rating "is the lowest of the individual subsystem ratings" [3]. There are no fractional classes. Promise fields are not checked at this point: they are what the vitals confirm in operation.

**Where the ideas come from.** Owner declaration before design, starting from business impact [5]; rating by the weakest subsystem, no fractional ratings, and outcome-based confirmation tests [3]; recovery objectives declared by the organization and verified by exercise [8, 9].

**How presets get values.** Preset promise values are set only by the validation programme, the file [`VALIDATION.md`](VALIDATION.md), through its experiment E1 and expert critique. They are frozen before use and published with a new Rulebook version, under the change process in the file [`GOVERNANCE.md`](GOVERNANCE.md). Until then, an owner who adopts a preset declares its structure and fills in its promise values. Comparability between such fabrics holds for the structure only, and the score record says so.
